# ADR-0009: Proof lifetime, replay, and nonce policy

- **Status:** Accepted
- **Date:** 2026-08-11

## Context

RFC 9449 requires DPoP proofs to be accepted only for a limited time after creation and allows servers to track `jti` values to reject replay. It also allows authorization servers and resource servers to issue server nonces. Nonces strengthen proof freshness and prevent useful proof pre-generation, but they add protocol state and retries.

The active MCP SEP-1932 conformance work uses a ±5-minute `iat` window and treats server-provided nonces as optional while testing both authorization-server and resource-server nonce handling when enabled.

## Decision

### Proof freshness

The v0.1 default verification policy is:

- maximum proof age: **300 seconds**;
- maximum accepted future clock skew: **300 seconds**;
- both values are explicit policy fields and may be tightened by deployments;
- zero, negative, overflowed, non-integer, or otherwise malformed `iat` handling fails closed;
- a server-provided nonce may be used to impose stronger server-clock freshness semantics without relying solely on client `iat`.

The default aligns with the current SEP-1932 conformance profile. High-assurance deployments should prefer tighter windows and/or nonce enforcement where client compatibility permits.

### Replay identity

A replay record is scoped to the verified proof key and request target context, conceptually:

```text
ReplayKey = SHA-256(
    proof_jwk_thumbprint ||
    canonical_http_method ||
    normalized_htu ||
    jti
)
```

The raw tuple may be represented differently internally, but implementations should avoid storing attacker-controlled unbounded `jti` strings directly when a fixed-size digest suffices.

The replay key deliberately does **not** include `ath`. Reusing the same proof identifier for a different access token must not create a new replay namespace.

### Replay lifetime

On first acceptance, the replay record must remain effective until that proof can no longer pass the configured freshness policy.

For an `iat`-based proof, the logical expiry is:

```text
replay_expiry = iat + max_proof_age
```

When an accepted proof is future-dated within the allowed skew, its store TTL from the current instant can therefore be as large as:

```text
max_proof_age + allowed_future_skew
```

Implementations may retain records slightly longer for storage/clock safety. They must never evict a replay record earlier merely because a local cache is under pressure and then silently accept the same still-valid proof again.

The replay operation remains atomic:

```text
check_and_record(replay_key, expiry) -> Fresh | Replay | StoreFailure
```

For deployments that require replay protection, a store failure fails closed. Multi-instance deployments need a backend whose atomicity/consistency scope covers all instances receiving requests for the same protected endpoint.

### Client nonce support

Keylix clients support both RFC 9449 nonce challenge classes in v0.1:

- authorization-server `DPoP-Nonce` / `use_dpop_nonce`;
- resource-server `DPoP-Nonce` / `WWW-Authenticate: DPoP ... use_dpop_nonce`.

Nonce state is scoped to the issuing server and is never shared across authorization servers or resource servers. A retry always creates a **new proof with a new `jti`** while incorporating the latest accepted nonce.

When a server provides a new nonce on a successful response, the client stores it for the next request to that issuer.

### Server nonce enforcement

Authorization-server and resource-server nonce enforcement are **supported but opt-in** in v0.1. The default verifier does not require a nonce that the server has never issued.

Once a server has challenged a client for a nonce, absence or mismatch of the required nonce cannot downgrade verification back to nonce-less acceptance for that challenge context.

Nonce values must be unpredictable when generated by Keylix-provided server helpers. Nonce state and replay state are separate concerns: reuse of an acceptable nonce does not permit reuse of a `jti`.

## Consequences

### Positive

- aligns with current RFC and SEP-1932 interoperability expectations;
- replay behavior is deterministic across single- and multi-process deployments;
- fixed-size replay keys bound attacker-controlled `jti` storage cost;
- client integrations can interoperate with nonce-enforcing authorization and resource servers;
- deployments can opt into stricter freshness without changing the proof format.

### Negative

- the ±300-second default is intentionally interoperability-oriented rather than maximally strict;
- strong replay protection in horizontally scaled deployments requires shared atomic state;
- nonce enforcement adds client/server state and retry behavior.

## Required tests

- proof exactly inside/outside past and future freshness boundaries;
- same `jti`/key/method/target replay rejection;
- same `jti` under another key does not collide;
- same `jti` at another target does not collide under the RFC target-URI replay context;
- access-token changes cannot bypass replay by changing `ath`;
- concurrent duplicate submissions admit at most one `Fresh` result;
- replay-store failure behavior;
- AS and RS nonce challenge/retry flows;
- new nonce on successful response;
- nonce mismatch and nonce downgrade attempts;
- retry produces a new `jti`.
